## 1. Overview

This TRD translates the [[PRD]] into a concrete technical design for the MVP: a public marketing site (no auth, no client portal) with a lead-capture contact form that must reliably notify the team by both email and Slack.

**Stack decision (confirms PRD §10):** Next.js + Supabase, **not** MERN. There is no Node/Express API server and no MongoDB. Next.js Route Handlers act as the thin server layer for anything requiring secrets (Supabase service role key, Resend API key, Slack webhook URL); everything else is static/SSG content served directly.

## 2. Tech Stack

| Layer | Choice | Notes |
|---|---|---|
| Frontend framework | **Next.js 14+ (App Router)** | Deployed on Vercel; static generation (SSG) for marketing pages, one Route Handler for form submission |
| Language | TypeScript | Applies to both frontend components and Route Handlers |
| Styling | Tailwind CSS (recommended, not mandated by PRD) | Fast to implement a brand-driven design system (PRD §10 brand expansion); swappable if the design system says otherwise |
| Database | **Supabase (Postgres)** | Single table for MVP: `leads`. No MongoDB. |
| Backend logic | Next.js Route Handlers (`app/api/*`) | Replaces a standalone Express server; runs server-side only, has access to secrets |
| Hosting | **Vercel** | Existing domain cut over via staged DNS per PRD §9 |
| Email delivery | **Resend** | Transactional email for lead notifications |
| Team notification (chat) | **Slack Incoming Webhook** | Posts to a designated Slack channel on new submission |
| Auth | None | Confirmed not needed for MVP (PRD §4, §10) |
| CMS | None | Case study and service content is static, authored in-repo (MDX or plain TSX) per PRD §6 — no CMS until Phase 2 |
| Analytics | None (deferred) | Per PRD §7 — intentionally out of MVP scope, added post-launch |

## 3. System Architecture

```
Visitor Browser
   │
   ├── GET marketing pages (Home, Services, Work, About, Investors)
   │        → Statically generated by Next.js, served via Vercel CDN
   │        → No server round-trip, no Supabase call
   │
   └── POST contact form submission
            → Next.js Route Handler: app/api/leads/route.ts
                 1. Validate + sanitize input
                 2. Insert row into Supabase `leads` table
                    (using service role key, server-side only)
                 3. Send notification email via Resend
                 4. Post notification message via Slack webhook
                 5. Return success/error JSON to the client
```

**Key architectural decision:** All writes to Supabase happen server-side via the Route Handler using the **service role key**. The browser never receives a Supabase key with write access. This keeps the `leads` table fully locked down at the database level (see §4.3 RLS policy) since there is no legitimate client-side write path.

There is no client-side Supabase read in MVP (no page displays lead data publicly), so no `NEXT_PUBLIC_SUPABASE_ANON_KEY` is required for MVP unless a future admin view is added (see Open Questions).

## 4. Data Models

### 4.1 `leads` table

The only data model required for MVP — stores every contact form submission (client or investor/partner inquiry, per PRD §6 item 5).

```sql
create table public.leads (
  id            uuid primary key default gen_random_uuid(),
  type          text not null check (type in ('client', 'investor')),
  name          text not null,
  email         text not null,
  company       text,
  project_type  text,          -- only meaningful when type = 'client'
                                -- e.g. 'web', 'app', 'saas', 'crm', 'design'
  message       text not null,
  status        text not null default 'new'
                check (status in ('new', 'contacted', 'archived')),
  created_at    timestamptz not null default now()
);

create index leads_type_idx on public.leads (type);
create index leads_created_at_idx on public.leads (created_at desc);
```

### 4.2 TypeScript type (shared between form and Route Handler)

```typescript
// lib/types/lead.ts

export type LeadType = 'client' | 'investor';
export type LeadStatus = 'new' | 'contacted' | 'archived';

export interface LeadInput {
  type: LeadType;
  name: string;
  email: string;
  company?: string;
  projectType?: string;   // required in practice when type === 'client'
  message: string;
}

export interface Lead extends LeadInput {
  id: string;
  status: LeadStatus;
  createdAt: string; // ISO 8601
}
```

### 4.3 Row Level Security (RLS)

RLS must be **enabled** on `leads` with **no public policies** — the table is only ever written to via the Route Handler using the service role key, which bypasses RLS by design. No `anon` or `authenticated` role should have insert, select, update, or delete access.

```sql
alter table public.leads enable row level security;
-- Intentionally no policies added: only the service role (server-side) can access this table.
```

## 5. API Contracts

MVP has exactly one API endpoint.

### `POST /api/leads`

**Request body:**

```json
{
  "type": "client",
  "name": "Jane Doe",
  "email": "jane@example.com",
  "company": "Acme Co",
  "projectType": "web",
  "message": "We need a marketing site rebuild and a lightweight CRM."
}
```

**Validation rules (enforced server-side in the Route Handler, not just the frontend):**

| Field | Rule |
|---|---|
| `type` | Required. Must be exactly `"client"` or `"investor"`. |
| `name` | Required. 1–200 characters, trimmed. |
| `email` | Required. Must match a standard email format. |
| `company` | Optional. Max 200 characters. |
| `projectType` | Optional. If present, must be one of `web`, `app`, `saas`, `crm`, `design`. |
| `message` | Required. 10–5000 characters, trimmed. |

**Success response — `200 OK`:**

```json
{
  "success": true,
  "id": "b3f1c2a0-1234-4a5b-8e9d-abcdef123456"
}
```

**Validation error — `400 Bad Request`:**

```json
{
  "success": false,
  "error": "VALIDATION_ERROR",
  "fields": {
    "email": "Must be a valid email address"
  }
}
```

**Rate limited — `429 Too Many Requests`:** returned when the abuse-prevention check in §7 trips.

**Server error — `500 Internal Server Error`:**

```json
{
  "success": false,
  "error": "SERVER_ERROR"
}
```

**Important behavioral contract:** the database insert (§4.1) must succeed before the endpoint reports success to the client. Email and Slack notification sends (§6) should be attempted but a failure in either **must not** fail the whole request or block the lead from being saved — see §8.4 for the exact degradation behavior. The lead record is the source of truth; notifications are a best-effort convenience layer on top of it.

## 6. Third-Party Integrations

| Service | Purpose | Integration point | Failure handling |
|---|---|---|---|
| **Supabase** | Postgres database for `leads` | Route Handler, service role key | If the insert fails, return `500` to the client — this is the one integration that must succeed for the request to succeed. |
| **Resend** | Sends the lead-notification email | Route Handler, after successful Supabase insert | If the email send fails, log the error server-side but still return `200` to the client (lead is already saved). See §8.4. |
| **Slack Incoming Webhook** | Posts lead-notification message to a Slack channel | Route Handler, after successful Supabase insert, in parallel with Resend | Same as Resend — best-effort, does not block the client response. |
| **Vercel** | Hosting, CI/CD from git, DNS cutover target | Deployment platform | N/A |
| *(Deferred)* Analytics tool | TBD — not selected for MVP | N/A | Out of scope for this TRD; revisit per PRD §7 open question |

## 7. Performance & Scalability Requirements

These map directly to PRD §7 success metrics.

- **Core Web Vitals (production, mobile):** LCP < 2.5s, CLS < 0.1, INP < 200ms.
- **Static generation:** Home, Services, Work, About, and Investors pages must be statically generated (SSG) at build time — no server-side data fetching on the render path for marketing pages, since content is static/in-repo for MVP.
- **Images:** All images served through `next/image` for automatic optimization, responsive sizing, and lazy loading below the fold.
- **Form submission latency:** `/api/leads` should respond within 2s under normal conditions. Email/Slack sends should not be awaited sequentially — fire them concurrently (e.g., `Promise.allSettled`) after the Supabase insert completes.
- **Abuse/spam protection:** Since `/api/leads` is a public, unauthenticated endpoint, apply:
  - A honeypot field (hidden form field that must remain empty) to filter basic bots.
  - IP-based rate limiting, backed by **Upstash Redis** (`@upstash/ratelimit` + `@upstash/redis`), sliding window, 5 submissions per IP per hour. **An in-memory limiter is explicitly ruled out** — Route Handlers run as stateless serverless functions, so in-process state does not reliably persist across invocations/instances and would not actually enforce the limit in production (security audit finding #1).
  - **Contingency, not built at MVP launch:** if spam volume proves the honeypot + rate limit insufficient, add a CAPTCHA challenge (Cloudflare Turnstile is the default choice — free, low-friction) gated behind a threshold (e.g., triggered after N suspicious submissions from an IP) rather than shown to every visitor by default.
- **Scalability ceiling for MVP:** Traffic and lead volume are expected to be low (agency marketing site, not high-traffic consumer product). Supabase free/starter tier and Vercel's default plan are expected to be sufficient; no horizontal scaling design is needed for MVP.

## 8. Non-Functional Requirements

### 8.1 Security
- No secrets (`SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`, `SLACK_WEBHOOK_URL`, Upstash credentials) are ever exposed to the client — they exist only as server-side environment variables, read inside the Route Handler.
- All user input to `/api/leads` is validated **and sanitized** server-side (§5) regardless of client-side validation, since client-side checks can be bypassed. Sanitization specifically means: HTML-escape `name`, `company`, and `message` before interpolating them into the Resend HTML email template; escape Slack's `mrkdwn` special characters (`&`, `<`, `>`) before building the Slack webhook payload. Never interpolate raw user input into either template as trusted markup (security audit finding #3).
- The Route Handler rejects any request that isn't `Content-Type: application/json` before touching the body (400/415), closing simple cross-site form-POST vectors even though CSRF impact is otherwise low (no cookie-based session exists).
- `/api/leads` sets **no CORS headers** and is same-origin only — this is a deliberate, documented policy, not an accidental default (security audit finding #5). Any future need for cross-origin access (e.g., an embeddable form on a campaign microsite) requires a reviewed, explicit origin allowlist — never a wildcard — and a follow-up security review before it ships.
- Every response sets standard security headers via `next.config.ts`: `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` (security audit finding #4).
- RLS is enabled on all Supabase tables with no permissive public policies (§4.3).
- HTTPS enforced everywhere (default on Vercel + custom domain).
- **Environment isolation:** Preview and development deployments use a **separate Supabase project** (not just a separate table) and separate Resend/Slack credentials from production, scoped per-environment in Vercel (Production / Preview / Development each get distinct values). This prevents preview-deployment traffic — which is reachable via public, non-authenticated URLs — from writing real rows to the production `leads` table or triggering real notifications to the team (security audit finding #2). Resolving this is a prerequisite for enabling any preview deployment, not a nice-to-have.
- Vercel, Supabase, Resend, and Slack admin accounts/orgs require MFA before launch; access is limited to team members who need it (security audit finding #8).

### 8.2 Accessibility
- Target **WCAG 2.1 AA** across all pages, given the site is itself a portfolio piece for a design/dev studio (PRD §3 goals).
- Contact form must be fully keyboard-navigable with visible focus states and properly associated labels/error messages (not color-only error indication).

### 8.3 Browser & device support
- Latest 2 versions of Chrome, Safari, Firefox, Edge; iOS Safari and Android Chrome for mobile.
- Fully responsive from 320px width up; PRD §7 requires mobile conversion parity with desktop.

### 8.4 Reliability / graceful degradation
- A `leads` row must never be lost due to a downstream notification failure. Order of operations in the Route Handler:
  1. Insert into Supabase → if this fails, return `500`, nothing else happens.
  2. On successful insert, attempt Resend email and Slack webhook concurrently, independently of each other.
  3. Log (server-side, e.g., Vercel function logs) any notification failure with the associated lead `id`, so a missed notification can still be recovered by checking the `leads` table directly.
  4. Return `200` to the client once the insert succeeds, regardless of notification outcome.
- **Alerting:** a lightweight threshold alert (e.g., a Vercel log-drain rule or a lightweight external monitor) notifies the team if `/api/leads` produces repeated `500`s or repeated notification-send failures in a short window, so a broken integration is caught proactively rather than discovered when someone notices leads have gone quiet (security audit finding #7). This does not need dedicated infrastructure — the simplest mechanism that produces a real alert is sufficient at current expected volume.

### 8.5 SEO
- Every page has unique `<title>`, meta description, and Open Graph tags (PRD §6 item 7).
- Semantic HTML structure (proper heading hierarchy, landmark regions) to support both SEO and accessibility.
- `sitemap.xml` and `robots.txt` generated at build time.

### 8.6 Maintainability
- Case study and service content authored as structured content (MDX or typed content objects) in-repo, not hardcoded inline in JSX, so Phase 2's CMS migration (PRD §8) doesn't require a full rewrite of page components.
- Shared `Lead`/`LeadInput` types (§4.2) used by both the form component and the Route Handler to keep client/server validation in sync.

## 9. Environment & Configuration

Required environment variables (set in Vercel project settings, never committed). **Each is scoped per Vercel environment (Production / Preview / Development) with distinct values for Production vs. Preview+Development** — preview and development share a separate Supabase project and separate Resend/Slack credentials from production (security audit finding #2):

| Variable | Used by | Exposed to client? |
|---|---|---|
| `SUPABASE_URL` | Route Handler | No |
| `SUPABASE_SERVICE_ROLE_KEY` | Route Handler | No — server-only, full table access |
| `RESEND_API_KEY` | Route Handler | No |
| `NOTIFICATION_EMAIL_TO` | Route Handler | No |
| `SLACK_WEBHOOK_URL` | Route Handler | No |
| `UPSTASH_REDIS_REST_URL` | Route Handler (rate limiting) | No |
| `UPSTASH_REDIS_REST_TOKEN` | Route Handler (rate limiting) | No |

No `NEXT_PUBLIC_*` Supabase keys are required for MVP, since there is no client-side Supabase usage (§3).

A committed `.env.example` (placeholder values only) documents this list for local setup; `.env.local` and all `.env*.local` variants are gitignored, and GitHub secret scanning/push protection is enabled on the repository (security audit finding #9).

## 10. Open Questions

The items below were resolved into concrete decisions above per the [[SECURITY_AUDIT|security audit]] (rate-limiting backend §7, environment isolation §8.1, security headers/CORS/sanitization §8.1, alerting §8.4, access control §8.1, secret hygiene §9). What remains genuinely open:

- ~~**Notification recipients**~~ — **Resolved.** `NOTIFICATION_EMAIL_TO` = `jarvisstudios12@gmail.com`. A Slack incoming webhook has also been provisioned; per §8.1/§9 secret-hygiene rules, the webhook URL itself is **not recorded in this document** — it is set directly as the `SLACK_WEBHOOK_URL` environment variable in Vercel (Production scope) and, separately, as a distinct value for the Preview/Development Supabase project's own test channel per the environment-isolation decision (ARCHITECTURE §4.9). Whoever provisions Vercel env vars for this project needs the value passed out-of-band (e.g., a password manager or direct message), not via this repo.
- **Admin visibility:** MVP has no admin UI — leads are only visible via the Supabase table editor or the email/Slack notifications themselves. If a lightweight admin view becomes necessary sooner than Phase 2, it would need its own `NEXT_PUBLIC_SUPABASE_ANON_KEY`, real authentication (not the service-role pattern), and its own RLS policy design (currently intentionally omitted per §4.3).
- **Styling approach:** Tailwind CSS is recommended in §2 but not confirmed by the PRD — worth confirming once the expanded brand/typography system (PRD §10) is finalized, in case it favors a different approach (e.g., CSS Modules, styled-components).
- **Dependency scanning in CI:** `npm audit` (and Dependabot/Snyk) should run in CI once `package.json` exists — no action needed until Phase 0 scaffolding begins (security audit finding #10).
