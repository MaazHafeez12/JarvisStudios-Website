## [Unreleased]

### Security
- **`next` 16.2.12 → 16.3.5, `sharp` override `^0.35.3` → `^0.35.4`, closing a CRITICAL advisory and two highs.** GHSA-p293-qw3h-jr36 (unauthenticated RCE on Windows-hosted servers) and GHSA-2xp9-vwfh-vxw4 (RCE in the Image Optimization API via AVIF) both covered `15.6.0-canary.0 – 16.3.2`, so the pinned version sat inside the range; `sharp` <0.35.4 carried two libheif advisories, and the repo's own `overrides` block was pinning it to the vulnerable line. `npm audit` now reports zero vulnerabilities.
  - **The failure worth recording is not the CVE, it's that CI had been reporting it the whole time.** `dependency-audit.yml` has run `npm audit --audit-level=high` on every push and weekly since 2026-08-05. It exits non-zero on a high, so it had been failing continuously and the signal was going unread — a check nobody looks at is indistinguishable from a check that does not exist. This was found only because installing an unrelated dev dependency printed the summary in passing.
  - **An audit that reads the workflow file is not an audit.** The review that preceded this change marked dependency management as covered on the strength of `dependency-audit.yml` existing and Dependabot being configured. Both were true and neither implied a clean result. The transferable rule: run the check, don't read the config for it.
- **The rate limiter's client identifier no longer trusts a client-supplied header** (`lib/client-ip.ts`, extracted from `app/api/leads/route.ts`). It read the *leftmost* entry of `x-forwarded-for`, consulting `x-real-ip` only when XFF was absent — which behind Vercel it never is. XFF is append-only and its leftmost entry is whatever the original caller claimed, so sending a different `X-Forwarded-For` per request yielded a fresh rate-limit bucket each time and the documented 5-per-IP-per-hour limit (`docs/TRD.md` §7) did not bind. Precedence is now `x-vercel-forwarded-for` → `x-real-ip` → the *rightmost* XFF hop, preferring headers the platform writes over ones the caller can forge, and falling back to a shared `"unknown"` bucket rather than a per-request one.
  - Moved out of the route handler in the process: a Next route file's exports are a framework contract and shouldn't carry helpers, and this needed to be testable without standing up a request. It takes `Headers` rather than the request for the same reason.
- **Three CSP directives that do not inherit from `default-src`** (`next.config.ts`): `base-uri 'none'`, `form-action 'self'`, `object-src 'none'`. A policy can look locked down and still leave all three open, because `default-src` does not cover them — an injected `<base href>` silently re-points every relative URL on the page, including the next script it loads.

### Added
- **A page per trade** (`/for/construction`, `/for/plumbing`, `/for/hvac`; `content/trades.ts`, `app/for/[trade]/page.tsx`). The site has been positioned for trades and local service businesses since launch — `/about` says so in its first paragraph — while containing almost none of the words that market searches with. **Measured across every content file before this change: "construction" four times, "trades" once, "plumbing" once, "roof" once, and nothing at all for HVAC.** Meanwhile the six service pages compete for "web development" and "CRM" against agencies with orders of magnitude more domain authority. "Software for plumbing companies" is a search this studio can plausibly win; "web development" is not.
  - **Three pages, not thirty-six, and the restraint is the point.** Six services times six trades spun from one template with the noun swapped is the doorway-page pattern Google penalises — correctly, because that is what it would be. A trade earns a page here when the operational problem is genuinely different: emergency call economics for plumbing, seasonal demand plus lapsing maintenance agreements for HVAC, estimating and unrecorded variations for construction. **Electrical and roofing are deliberately omitted** — their call-and-quote economics are plumbing's with a different tool in the van, and a near-duplicate of a page already here costs more than it earns.
  - **561, 555 and 572 words of trade-specific copy**, each with its own H1 carrying the search phrase in a readable sentence, its own title and description, and `WebPage` + `FAQPage` + `BreadcrumbList` structured data. `WebPage` rather than `Service` deliberately: a trade page describes four offers and links out to each, so typing it as a `Service` would put a seventh service into a catalogue that has six. The `audience` node is what carries the meaning.
  - **They exist as much for internal linking as for their own rankings.** Each page links out to the service lines that genuinely apply, which gives those pages inbound links from a page about the *problem* rather than from another copy of the category page. The footer gains a fourth column — derived from `TRADES`, like the service links — because there is no `/for` hub and without it these pages would be reachable from the sitemap and nowhere else.
  - **No `/for` hub, deliberately.** A three-item index whose only content is three links the footer already carries sitewide is a thin page, and the breadcrumb graph names Home as the parent rather than a URL that would 404.
  - **Held to PRODUCT.md Principle 1, which bites harder here than anywhere else on the site**, because an industry page is where the temptation to imply a client list is strongest. No page says or implies the studio has done this work for this trade. `proofFrom` *pulls* a published `ServiceProof` out of `content/services.ts` rather than restating one — it is a `ProjectType`, not a string, so a result cannot drift from its source or be invented beside it. Only `construction` sets it, because SNF Construction Group is the only real client result the site publishes.
  - **What is not signed off is flagged in the file header**, the same way `content/service-detail.ts` flags its own: the operational claims — that the out-of-hours gap is where plumbing loses most jobs, that maintenance agreements lapse for want of tracking — are reasoned from the market the site already addresses, not supplied by the business or measured. They read as expertise. Review them as copy.
  - The sitemap went from 17 URLs to 20.
- **`docs/CASE_STUDY_BRIEF.md`** — the questions to ask a client and the written consent that has to exist before a second case study can be published. `TODO.md` has carried the case-study item since launch, blocked on information only the client has. **The block was real; treating it as un-actionable was not.** A case study is made entirely of the four things Principle 1 forbids inventing — results, clients, metrics, testimonials — so there is no draft-now-verify-later version of it. What there is, is a list to send. It also records where a collected result lands: a `ServiceProof` in `content/services.ts` as the single source, an insight with `kind: "case-study"`, and `proofFrom` on any trade page that matches.
- **IndexNow submission after a production deploy** (`scripts/indexnow.mjs`, `.github/workflows/indexnow.yml`, `public/ff3ba3dad840a6b79c54255dc6f3b415.txt`, `npm run indexnow`). Bing recrawls submitted URLs within hours instead of whenever it next chooses to. **Google does not participate in the protocol and is unaffected** — it discovers changes through the sitemap submitted in Search Console, which is the actual mechanism for the other half of search traffic. This matters here because insight posts ship one at a time, and each one currently waits on a crawl nobody controls.
  - **Triggered by `deployment_status`, not `push`.** Vercel deploys `master` independently of CI, so a job on the push would race the deploy and submit URLs whose new content is not being served yet — telling a crawler to come now, for the old page. The cost of that choice is a silent failure mode, recorded in the workflow: if the Vercel GitHub integration is disconnected, or labels its production environment as anything other than `Production`, this stops firing and reports nothing rather than failing red. `workflow_dispatch` and `npm run indexnow` are the manual paths.
  - **The key is committed deliberately, and is not a secret.** The protocol's entire ownership proof is that `https://<host>/<key>.txt` is publicly fetchable — the engine reads it over the open internet before accepting a submission — so holding it in an env var would mean publishing it verbatim anyway. What it grants someone who copies it is the ability to ask Bing to re-crawl pages already listed in the sitemap.
  - **It preflights the key file rather than letting the API do it**, because a rejection arrives as a bare `403` that does not say which half is wrong. It also reads `SITE_URL` back out of `lib/seo.ts` instead of restating the domain: that constant exists precisely so the origin is declared once, and a script hardcoding it would be the fourth place for it to drift.
  - **It submits all 17 sitemap URLs, not only the changed ones**, which is not what the protocol asks for. At 17 URLs and a handful of deploys a week the distinction costs nothing; the script header records that the fix at a few hundred pages is to derive the list from the deploy's diff, not to submit less often.
  - **Exercised end to end in production.** The `deployment_status` trigger fired on the #44 production deploy (2026-09-22) and the run logged `indexnow: 200 accepted — 20 URLs for jarvisstudios.net`, which also shows the list tracking the sitemap as it grew from 17 to 20 URLs. That clears the one gap this entry originally recorded: before go-live only a dry run was possible, and it could check the sitemap parse and the preflight refusal but not the trigger.
- **A page per service line** (`/services/<id>`, `content/service-detail.ts`, `app/services/[slug]/page.tsx`). All six services previously lived on `/services` as fragment anchors, and **a fragment is not a separate URL to a crawler** — so one ~1,000-word page was competing for "web development", "CRM", "SaaS", "app development", "AI automation" and "marketing & design" simultaneously, and could rank for none of them because it was not *about* any of them. Measured before the change: ~170 words per service, and not one heading on the page contained the word "CRM" or "development".
  - **Each page now carries 604–729 words**, its own title, description, canonical, an H1 holding the search term inside a readable sentence, and `Service` + `FAQPage` + `BreadcrumbList` structured data. The sitemap went from 11 URLs to 17.
  - **`/services` is untouched as a comparison hub and its DIRECTION CONTRACT still holds** — every service keeps its name, summary, all three capabilities, its proof and its CTA in every state. Comparison is a job a set of separate pages structurally cannot do, which is the entire reason the grid exists. These pages are depth hanging off the hub, reached by a second link on each card; they are not a replacement for it.
  - **The copy is separated from `content/services.ts` for a bundle reason, not a tidiness one.** `ServiceExplorer` is a `"use client"` component that imports `SERVICES`, so anything in that file is serialised into the client bundle and shipped to every visitor of `/services`. Putting six ~4KB essays there would send all of them to every browser in order to render a grid that displays none of them.
  - **`FAQPage` is doing double duty.** For search it is eligible for rich results; more reliably, it is the shape an answer engine can lift a response from and attribute to a URL. The questions are service-specific rather than one shared set reworded, because identical answers repeated across six pages is duplicate thin content that costs more in ranking than the markup gains.
  - **Held to PRODUCT.md Principle 1.** Every `outcomes` entry restates a capability already published in `content/services.ts`; the commercial answers restate figures from `content/engagement.ts` already marked as supplied by the business; proof still appears only on `design`, the one line that has any. **What is not yet signed off** is flagged in the file header: the *stances* in the body copy ("we'd push back on a brief that asked for it", "rewrites are the most commonly over-prescribed fix") are inferred from positions the site already takes elsewhere, not supplied, and read as commitments a client could hold the studio to.
  - **`InsightPost` gains an optional `services` tag**, used to build related reading. Most posts deliberately leave it unset: `four-steps` and `why-we-quote-scope-not-a-price-list` apply to all six equally, and tagging them with all six would put the same two links on every service page, which is padding rather than relevance.
- **A privacy policy and terms of use** (`/privacy`, `/terms`, `content/legal.ts`, `components/LegalPage.tsx`). The contact form has been collecting name, email, company and free text from EU-reachable visitors into Supabase since launch with no privacy notice anywhere on the site, which is the clearest compliance gap the site had.
  - **Every factual claim is derived from the code rather than drafted from a template**, and the content file says so in a header that names each source: the collected fields are `LeadInput`; the sub-processor list is exactly what `app/api/leads/route.ts` touches (Vercel, Supabase, Upstash, Resend, Slack); the "no cookies" claim is literal, the only browser storage being the `theme` key that never leaves the device. **The IP disclosure exists because `checkRateLimit()` keys on it** — an IP is personal data, and a policy listing only the form fields would have been incomplete. A policy that has drifted from the implementation is a published false statement about someone's data, so the file asks for both to change in the same commit.
  - **Written jurisdiction-neutral, granting GDPR-tier rights to every visitor.** Honouring the strongest common set of rights for everyone meets or exceeds the other major regimes and avoids naming a governing law that isn't settled. The terms therefore carry **no governing-law or venue clause** — recorded in the file as a deliberate omission to close once an entity is registered, on the grounds that a venue clause naming the wrong place is worse than none. The controller is the trading name plus an email, which is thin against GDPR Art. 13(1)(a) and flagged as such.
  - **A collection notice sits on the form itself**, not only in the footer, because Art. 13 asks for the information to reach someone as they hand data over. It states the 24-month retention inline: "see our privacy policy" alone tells a visitor nothing at the moment they are deciding whether to type.
  - **`LegalPage` deliberately does not scroll-reveal its body**, unlike every other long-form page here. People arrive at a policy hunting one clause — usually how to get their data deleted — and scroll fast; content that fades in as you reach it makes a reference document harder to scan, which is the opposite of what the motion is for.
  - **`ContactFormSkeleton` was updated in the same change.** The notice makes the form taller, and that skeleton is what holds down a documented 0.43 CLS regression — a skeleton one element short has stopped doing its job.
- **Canonical tags, the Open Graph fields Next can't infer, and schema.org structured data** (`lib/seo.ts`, `lib/structured-data.ts`, `components/seo/JsonLd.tsx`).
  - **Narrower than it first looked, and the correction is the useful part.** The review that prompted this reported "no Open Graph or Twitter cards" — wrong. `app/opengraph-image.tsx` is a file convention at the app root, so Next was already synthesizing `og:title`, `og:description`, `og:image*` and the full `twitter:*` set per page. Checking the rendered `<head>` rather than grepping for an `openGraph` key is what caught it. What was genuinely absent: `<link rel="canonical">` on every route, `og:url`, `og:type`, `og:site_name`, `article:published_time`, and all structured data.
  - **`pageMetadata()` now supplies those on all eight routes**, and `SITE_URL` is defined once instead of being repeated in `sitemap.ts`, `robots.ts` and `metadataBase`. Insight posts report `og:type: article` with a publication date.
  - **`Organization` + `WebSite` on the homepage, `BlogPosting` + `BreadcrumbList` on each article.** Held to the same bar as visible copy (PRODUCT.md Principle 1): every value is already published in human-readable form on the site. That rules out `LocalBusiness`, which wants an address and geo — inventing those to satisfy a schema is exactly the failure mode the principle names — along with `AggregateRating`, `sameAs` and `foundingDate`. `dateModified` equals `datePublished` because no modified date is tracked and claiming a fresher one would be a fabrication.
  - **`JsonLd` escapes `<` as `<`.** `JSON.stringify` output inside a `<script>` element meets a parser looking for `</script`, which does not care that it is inside a JSON string. A precaution today, since every value is studio-authored — it stays because the day a CMS field reaches a graph, the escaping needs to already be there.
- **Unit tests, and a runner** (Vitest; `npm test`, `npm run test:watch`; 58 tests over `lib/`). Scope is deliberately the three pure security-relevant functions — `validateLead`, the escaping pair, and `getClientIp` — where a quiet regression has a consequence worse than a visual glitch and the cost of covering it is a sub-second suite with no I/O. The spoofing case in `client-ip.test.ts` is a regression test in the literal sense. **Component and end-to-end coverage is still absent**, recorded in `vitest.config.mts` as a real gap rather than implied to be covered.
- **A build/lint/test CI gate** (`.github/workflows/ci.yml`), kept separate from `dependency-audit.yml` so a red X says which kind of thing broke without opening the logs. It caught a lint error in `global-error.tsx` on its first run, which is the gate working. **It reports but does not gate**, since pushes to `master` deploy via Vercel independently — making it a real gate needs branch protection, noted in the README.
- **Route-level and root-level error boundaries** (`app/error.tsx`, `app/global-error.tsx`). A render error previously fell through to Next's built-in page: on a production build, a bare "Application error: a client-side exception has occurred" with no nav and no way back. `error.tsx` renders inside the layout and is shaped like `not-found.tsx`; `global-error.tsx` handles the case where the layout itself threw, which is why it is plain inline styles — the token layer is exactly what is unavailable. It surfaces `error.digest`, the only handle tying what a visitor saw to a server log entry.
- **Conversion tracking on the contact form.** Page views were tracked; the one conversion was not, so "how many visitors actually enquire" — the only number that matters for a lead-generation site — was unanswerable. `lead_submitted` fires on success and `lead_submit_failed` carries a reason, the latter being the operational one: a spike means leads are being lost, which otherwise surfaces only when someone notices the inbox has gone quiet. **The payload is `projectType` and nothing else** — one of six enum values chosen from a dropdown. Nothing the visitor typed is sent; routing name, email or message through a second processor would make the privacy policy untrue.

- **A case study in `/insights`** — SNF Construction Group's 10% month-over-month social reach growth (`content/insights.ts`, slug `snf-construction-group-social-reach`). It introduces **no new facts**: the client name, the figure, the "content and social management on a retainer, measured monthly since takeover" framing are all already published in `content/services.ts` (`ServiceProof` on the `design` line) and the homepage featured-work section. The piece restates that one number and explains what makes it credible — compounding vs. a spike, why the engagement is a retainer not a fixed scope (per `content/engagement.ts`), why a measurement window makes a percentage mean something — and is explicit about what it deliberately omits (no vanity baseline, no invented tactics list, no self-written quote).
  - **`InsightPost` gains an optional `kind: "note" | "case-study"`**, defaulting to a note. Only the label treatment reads it: the listing and detail pages prefix the date with "Case study · " when set. The file header's old "these are not case studies" note is rewritten to describe the stricter bar a case study is held to instead. `app/sitemap.ts` picks the new slug up automatically — it already maps over `INSIGHTS`.
- **A favicon** (`app/icon.svg`, `app/apple-icon.png`). The site had none — not a wrong one, none at all: no icon convention file in `app/`, and `/favicon.ico` returning 404 in production — so every tab showed the browser's fallback globe. Next's App Router file convention does the registration, so `layout.tsx` is untouched; the build now emits `/icon.svg` and `/apple-icon.png` as static routes and injects both `<link>` tags.
  - **It is deliberately not `public/logo.svg` renamed**, which is the obvious move and produces an invisible icon for half the audience. That file is the *on-dark* brand asset — its own header says the "J" ships white — and tab bars follow the OS theme, so a white-on-transparent mark disappears on a light one. Giving the icon its own `#141414` tile (neutral-950, taken from `tailwind.config.ts` rather than eyeballed) means it stops borrowing the browser's background and reads the same in both themes.
  - **The mark is also not square** — 285.06 × 214.44, roughly 4:3, against a favicon slot that is square everywhere it renders. It is fitted rather than stretched: scaled to 400 of 512 wide and centred, which is as large as it goes before the tile starts reading as cropped. Colours are untouched, per `docs/DESIGN.md` §2.1's rule that the neutral/blue letterform split is the mark's signature.
  - **`apple-icon.png` is rasterised from the same SVG** at 180×180 via sharp, so the two cannot drift. Apple's touch icon does not accept SVG, which is the only reason a second file exists; iOS applies its own rounded mask over the full-bleed tile.
- **Scroll-scrubbed stages — one mechanism, four sections** (`docs/MOTION_REDESIGN.md` §5.8, direction recorded as §2's third amendment). Direction given with theradiuslab.com as the reference, and the complaint behind it was precise: the tours *step*. An `IntersectionObserver` swaps which vignette is showing, so between wipes nothing moves at all — a step, a hold, a step. Scrubbing means the section moves exactly as far as the visitor moved it and stops when they stop.
  - **`lib/use-scroll-progress.ts` writes one number.** `--p`, 0 to 1 across a track, set on the pinned element; every derived value is CSS arithmetic off it. A beat's fade-in / hold / fade-out is `min()` of two ramps against sub-ranges of `--p` — the convention is documented once in the `.stage-*` block of `globals.css` rather than re-derived per section. No JS computes a transform, an opacity or a colour. **No GSAP, no Lenis, no `scroll-timeline`**: §7's "not needed, not added" still holds, and the reference site turns out to do the same thing — `position: sticky`, one custom property, `calc()`.
  - **It is a hook, not a component**, because the two tours own their DOM: their track is a two-column grid and the pinned stage is one of its children, so there is no wrapper to hand them. `components/motion/ScrollStage.tsx` is a thin shell for everything else.
  - **`--p` is a registered `@property` of `syntax: "<number>"`.** The style system stores a parsed number instead of re-tokenising a string every frame, and its `initial-value: 0` is simultaneously the server render, the pre-hydration frame, the no-JS state and the reduced-motion state. Every stage is authored so `--p: 0` is a coherent resting frame, never a blank one.
  - **A new `/services` film section** (`components/motion/ThreadFilm.tsx`): a frame that starts as a card and grows into the viewport with its corners melting from 34px to square, four beats fading through beside it on their own sub-ranges. Beat timings were tuned against a measured legibility sweep, not by eye — the first handoff left 226px of scroll with nothing readable where every other left ~110px, and the closing beat ended inside the track, leaving the last 3% an empty frame.
  - **Its resting frame is authored, not captured** (`ThreadStill.tsx`): a weave with one thread pulled, drawn on `currentColor` in the same family as the ten vignette scenes. The section is complete before the video loads and stays complete if it never does. `ScrubVideo.tsx` holds a `requestVideoFrameCallback` seek-lock so a fast scroll cannot queue seeks faster than the decoder retires them, and stays transparent until `loadeddata` rather than painting a black box over the still. **The source ladder ships empty** — no footage exists yet, and pointing at absent files would cost every visitor a failed request for no picture. Encodes must be **all-intra**; with a normal GOP a backward scrub decodes most of a keyframe group per frame and no code fixes it.
  - **The homepage hero pins for 250svh**, and its second act is the shard field closing. `lib/hero-shards.ts` holds the field in two arched bands kept off the copy by `Y_INSET`; that inset exists to protect the headline, so once the headline has ridden out it is released and the bands converge on the space it left — narrowing on X as well as Y, so the field gathers rather than flattening. `.hero-shard-mask` opens on the same schedule, since the mask and `Y_INSET` are the same guarantee twice. **The scrub only ever moves copy *out***, so `--p: 0` is the untouched hero and the LCP headline never waits on a scroll event.
    - **Corrects an earlier claim in this entry's own history.** The hero first shipped at 125svh on the reasoning that the field is an *annulus* and the centre is therefore empty by construction, making a second act impossible without new geometry. That was wrong: `hero-shards.ts:48-58` records that an annulus was the first idea and was rejected in favour of two bands. A constant can move; a ring cannot. Checking what the geometry actually is, rather than trusting a remembered description of it, is the transferable part.
  - **Measured at the §7 mid-tier baseline** (375×812, 4× CPU, 4 cores, production build, continuous fling rather than the stepper §7 warns gives a false 60fps): **both tours hold 60.0fps with zero frames over 32ms**, against 55.6fps / 66ms / 4 LoAF for the same section before this pass. The hero and the film measure 50–59fps and 43–59fps respectively — **stated as ranges on purpose**: the film, with no code change, measured 59.2fps early in a session and 42.9fps late in the same one, and an interleaved A/B of the hero swung 54.6→59.6fps within a single arm. Thermal state moves this method by ~±5fps. §7 now records how to read that, because a single run cannot separate a regression from a warm laptop. The hero's convergence is perf-neutral by that A/B: `--len` 250 measured 58.5fps mean against 56.7 for 125.

### Changed
- **Tailwind CSS 3.4.19 → 4.3.3** (Dependabot #6). The theme moved from `tailwind.config.ts` (deleted) into an `@theme` block in `app/globals.css`, PostCSS now uses `@tailwindcss/postcss` (`autoprefixer` removed, since v4 handles prefixing itself), and every `bg-[--var]` token class became `bg-(--var)`. **The bar was that a visitor can't tell anything changed, and it was measured, not eyeballed.** Every element on all 21 routes had its computed styles and position captured at 1280 and 375 wide in both themes, on `master` and again on this branch, with full-page screenshots pixel-diffed alongside. Two v3 captures diffed against each other first set the noise floor: articles caught mid-fade differ by up to 0.35% of pixels, and nothing else moves. After the fixes below, every remaining pixel difference is one that also appears between two v3 captures.
  - **The upgrade tool leaves real breakage behind, and only the diff found it.** `vignette-kit.tsx` wrote `text-[--text-secondary]${…}`, and the tool skipped the class because an interpolation followed it directly. v4 reads the old form as nothing, so every service vignette's ink went from grey to white on 3,656 elements. Nothing fails the build when this happens.
  - **Three places where v4 fixes something v3 got wrong were reverted to what production actually renders**, because a version bump is the wrong place to ship design changes: (1) the nav's `bg-[--surface]/90` has never worked, since v3 can't put an opacity modifier on a bare variable and silently drops it, but v4 honours it. It was removed, with a comment in `Nav.tsx` saying the frosted bar is one class away. (2) The homepage h1's `sm:text-6xl` also set `line-height: 1` in v3, overriding `leading-tight` from `sm` up. In v4 an explicit `leading-*` wins, which grew the headline 45px taller, so it now says `sm:leading-none`. (3) v4's preflight drops v3's gray-200 default border, the pointer cursor on buttons (1,748 elements), and the gray-400 placeholder, which in v4 inherits the text colour at 50% and would make /contact's hints read as filled-in values. All three are restored in `@layer base`, with the reasons given there.
  - **One deliberate difference: `hover:` now applies only on devices that can hover.** It changes nothing on a desktop. On a phone, a tapped link no longer stays stuck in its hover style after the tap, which fixed a bug rather than changing the design.
  - **The tool wrapped the ~1,300 lines of custom CSS in `@layer utilities`, and that is what keeps the cascade intact.** Left unlayered, v4 would have ranked it above every utility regardless of specificity. In the same layer, after the utilities, it wins ties exactly as it did under v3.
  - Browser floor is now Safari 16.4, Chrome 111 and Firefox 128, all within `docs/TRD.md`'s "latest two versions" target.
- **React 19.2.8 → 19.3.0, `@react-three/fiber` 9.7.0 → 9.8.0, `@upstash/ratelimit` 2.0.8 → 2.1.0** (Dependabot #45, #46), with `react-dom` and both `@types` packages moved in step. **Merging #46 on its own would have left the tree in an unsupported state**: fiber 9.7.0 declares `react >=19 <19.3` because it ships its own reconciler bound to React internals, and npm only warns about a peer violation — it installs anyway. 9.8.0 widens the range to `<19.4`. The hero's WebGL canvas was checked in a production build, not only the type check. Five older Dependabot PRs (#30, #31, #33, #34, #35) were closed without merging, since `package.json` had already passed each of their target versions.
